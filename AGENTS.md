# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this is

A personal Trading 212 investment tracker in two parts:

- `worker/` — a Cloudflare Worker with a D1 database. It measures the portfolio on a schedule, stores history, fetches optional external data and serves everything as JSON.
- `docs/` — a static website (GitHub Pages) that renders that JSON. No build step needed to run it and no CDN libraries; the only library is Preact with htm, vendored in `docs/vendor/`. The Pages deploy publishes a minified copy built by `tools/bouw-site.mjs` (the classic scripts from `index.html` merged into `js/app.js`, the rest minified); `docs/` stays the source, and `SITE=_site` runs the browser checks on the built copy.
- `apps-script/` — the legacy Google Sheets version. Leave it alone unless asked.

The user-facing language is **Dutch**: all UI text, code comments, commit messages and READMEs. Keep it that way. Write plain, neutral Dutch, sentence case, no marketing tone.

## Hard rules

- **No secrets or personal data in the repo.** It is public. API keys, tokens, the SEC contact address and portfolio figures live in Cloudflare secrets or the Worker's `kv` table, never in code, fixtures or commits.
- **Never type keys, tokens or passwords for the user**, in the site or in any dashboard. The user enters them.
- **Respect data sources.** Do not spoof a browser User-Agent, do not work around a refusal (403, 520, robots.txt), do not scrape sources that disallow it. If a source refuses the Worker, report it and offer the official route (an API key or a manual upload).
- **The base must work with Trading 212 alone.** Every other source is optional and must fail soft: a missing key or failed fetch hides or explains a tile, it never breaks the page.
- **Not investment advice.** Risk suggestions and alternatives are worked examples. Keep the existing disclaimers when touching those texts.

## Worker conventions

- Free plan D1 limit: **5 million rows read and 100,000 rows written per UTC day**. D1 counts every row a query scans, not the rows it returns. Never add a query that scans a whole growing table on every tick or request: filter on an indexed column (`intraday.ts`, `hours.hour`, `days.day`, `ext_prices.day` have indexes; new ones go in `LATE_INDEXES` so existing databases get them too), compute aggregates in JS from rows you already read, and cache what changes rarely (see `marketDataCached`, `dbWatch`). `countingDb` adds the real `rows_read`/`rows_written` to `cf_usage`; the settings page shows them next to the limits. From 70% of a daily D1 limit the Worker sends one push; from 85% it is in save mode until midnight UTC (`saveMode`): it keeps measuring, builds the overview at most every 30 minutes (`buildAllowed`), skips `marketStep`, and tells the site via `X-Tracker-Save` to refresh less often. The Worker runs on `*.workers.dev`, where the Cache API does nothing, so do not rely on `caches.default`. `buildData` does not read the history: it keeps today's figures and the latest positions in `todayState` (kv `today_state`), which reads only the measurements added since the previous build. What needs the whole history (all-time high and low, average daily range) is calculated by the site from its own series. The full series are built only when a device asks for them (`seriesFull`, for a new device, an old site version or the share link) through `seriesRows` (a kv cache, refreshed when `last_hour`, `last_day` or `series_ver` change); normal refreshes fetch only new rows (`seriesDelta`). Anything that writes `intraday`, `hours` or `days` must call `invalidateSeries` (this also resets `today_state`); code that only deletes old `intraday` or `hours` rows calls `invalidateRecent` instead. Days of earlier years sit in a separate cache (`series_old`) that only changes with `series_ver` or the new year, so calling `invalidateSeries` for routine clean-up would make every hourly round re-read all earlier years. Orders are cached the same way: anything that writes `orders` must call `invalidateOrders`. Market data (`marketDataCached`) keeps the price histories of the previous version and re-reads only the symbols whose prices changed: code that writes `ext_prices` passes those symbols to `bumpMarket(env, syms)`; `bumpMarket(env)` without symbols forces a full rebuild (also done every `MARKET_CACHE_MS`). D1 allows at most 2 MB per row, so large kv values go through `setBig`/`getBig`, which store them in parts (`key#1`, `key#2`, …); never write the overview, the share copy or a cache with plain `setKv`. Two Worker tests guard this: every SQL string in the Worker goes through SQLite's query planner and a full `SCAN` of a growing table fails unless it is listed in `SCAN_OK` with a reason, and a test with five years of data (30 positions, long names, 1,500 orders) fails when a 10-minute round reads more than 3,000 rows, an hourly round more than 5,000, the day estimate exceeds 400,000, a new device's full series request more than 80,000, or any kv row is 2 MB or larger.
- Free plan: at most **50 subrequests per invocation**. `marketStep` does one queued task batch per call (max 30 external calls). Queue new work in `planMarket`; do not fetch in loops inside a request.
- Keys: `withKeys(env)` merges Cloudflare secrets with keys saved through the site (`kv` key `keys`). Cloudflare secrets win. New key names go in `KEY_NAMES`.
- A new Cloudflare secret only becomes active after the next Git build; keys saved through the site work immediately.
- Schema changes go in the embedded `SCHEMA_SQL` (`ensureSchema` applies it). Use `CREATE … IF NOT EXISTS`.
- FMP has a daily budget (counter in `kv` `fmp_calls`). Keep previous data when a fetch fails.
- Record source failures with `noteExtError(env, source, msg)`; the site shows them under *Koppelingen*.
- Every external source needs a fallback where one exists. Use `srcFail` / `srcOk` / `srcDown` / `srcBackup` (`kv` `src_health`): on a limit or repeated failures, switch to the backup and record which backup did the work. Never retry a refused source in a loop.
- Write the built data only through `saveDataCache(env, data)` (it stores `data_core`, `data_extra` and their ETags; the series ETag stays as `seriesFull` left it). The share copy is built when someone opens the share link (`shareBody`, kv `share_stamp`), not on every build. New top-level fields that change rarely belong in `EXTRA_KEYS`.
- Push alerts go through `alertOnce(env, key, msg)` so each alert is sent once; only evaluate them when `pushSubs(env)` is non-empty.
- All `/api/*` routes require the `WEB_TOKEN` (prefer the `Authorization: Bearer` header; `?token=` is only kept for old clients and the Apps Script); only `/cal/<token>.ics`, `/share/<token>` and `POST /api/login` are public. `/share` serves a read-only copy without notes, accounts or keys, with money scaled when amounts are off. `/api/login` returns the `WEB_TOKEN` only when the posted Trading 212 key and secret match the ones in the Worker (constant-time compare, max 10 failures per hour, nothing stored).

## Site conventions

- The site is plain JS split over `docs/js/NN-*.js`. These are **classic scripts, not modules**: they load in the order of the `<script>` tags in `index.html` and share one global scope, so a top-level `const` or `function` in one file is usable in the next. Keep that order; code that runs while a file loads may only use names from the same or earlier files. Every top-level name is global: give new ones distinct names and avoid browser globals (`name`, `status`, `print`, `open`, …).
- Put new code in the file for its topic, or a new numbered file (then add it to `index.html` and `sw.js`). Follow the existing helpers: `eur`, `seur`, `spct`, `kvList`, `stat`, `bars`, `spark`, `lineChart`, `fill`, `clickable`.
- Own helpers in `00-kern.js`: `defineView(name, draw)` registers a part of the page; `renderAll()` draws the views of the open page and `refresh('plan')` only that one, and a failing view does not break the rest. A view that belongs only to pages that are not open (`PAGE_VIEWS`) is not drawn but marked stale and drawn when its page opens, so `refresh()` may list every view a change affects. `renderAll()` returns a promise: it yields to the browser (`yieldNow()`) between views once a slice takes more than 40 ms. Prefer `refresh('naam')` over `renderAll()` when only one view changes. Scripts that only one page needs can load lazily through `VIEW_SCRIPTS` in `10-navigatie.js` (not in `index.html`, but in the `sw.js` precache list). Long lists show a first part with `moreRows(key, rows, n, view)`. `tpl` is a tagged template that escapes inserted values (`raw()` for HTML that is already safe); prefer it over string concatenation with `esc()` in new code.
- Components: new or rebuilt pages may use Preact with htm (`import { html, render, useState } from '../vendor/preact-htm.js'`) in an ES module like `nieuws-preact.js`. A module loads after the classic scripts and may use their globals. Register it on `window` and let the classic code fall back to its HTML version when the module is not there (see `renderNews`). Do not load libraries from a CDN: vendor them so the app keeps working offline.
- Amounts must go through `eur`/`seur` so the "bedragen verbergen" toggle works.
- Colours come from CSS variables (`--page`, `--surface`, `--bg`, `--rule`, `--ink`, `--accent`, `--gain`, `--loss`, …), documented at the top of the "Eén geheel" block at the end of `style.css`. Themes are per device (`tracker.theme`: `light`, `dark`, `amoled`, `auto`; auto follows the system between light and dark only). Light is the base; dark overrides live under `:root[data-theme="dark"]`, and amoled is dark plus `data-amoled="1"` on `<html>`, so `:root[data-theme="dark"][data-amoled="1"]` only overrides surfaces and rules. Check light, dark and amoled.
- The accent colour is per device (`tracker.accent`, a `#RRGGBB`; presets in `ACCENTS`). `accentVars()` in `00-vroeg.js` derives `--accent` (at least 4.6:1 against the page, lighter in dark and amoled), `--accent-dark`, `--accent-soft`, `--accent-tint` (light fill, e.g. the menu pill) and `--on-accent` (text on an accent fill) and sets them inline on `<html>`; `setThemeAttrs()` applies theme, accent and `<meta name="theme-color">` before the first paint. Never hard-code the accent: use the variables in CSS and `C.accent`/`C.soft` in charts. After a theme or accent change call `themeChanged()` (redraws, because charts read `C`). `--gain` and `--loss` never follow the accent.
- Shell: desktop `.topbar` (logo, `#top-mini` with value and today's change, `.pillnav` with the sliding `.pill`, eye, refresh, gear) and phone `.m-top` (page title, eye, gear) plus `.m-tabs` (five pages, `.m-tab-ind` pill). `placeIndicators()` moves the pills; while Instellingen is open `body.set-open` fades them and turns the gear. Page switches go through `showPage()`: the old page gets `.pg-out` for `PAGE_OUT_MS` (170 ms), the new one `.pg-in` with `data-dir` `r` or `l` (menu order); Instellingen comes up from below. Animate only `transform`/`opacity`, use fill-mode `backwards` (a lingering transform makes the page a containing block for `position: fixed`), and skip it when `reduceMotion()`. Scrollbars are hidden; buttons scale to .96 on `:active`.
- Overzicht (design H1-A, v74) has its own marked section "Overzicht" at the end of `ontwerp.css`, all inside `@media screen` so the pdf report keeps its print layout. Desktop: the hero text sits over a full-width chart (`lineChart` set option `fill` draws the light area; `top: .44` keeps the line below the text), pins come from `heroMarkers` with a `kind` (`high`, `dep`, `buy`, `sell`) that sets the colour and the legend (`heroLegend`, `#hero-legend`), the KPIs are one strip (`.kpi-strip`), and every `.dash-sec` is a grid with the sticky `.section-head` on the left and the content on the right (stacked below 1000 px). Stijgers and dalers are two lists (`moverLists`, `.mv-row`) in the Vandaag section. The phone stacks everything, with a subtitle per section (`.m-head-sub`). Sections fade in on scroll via `animation-timeline: view()` (fill-mode `backwards`, only with `data-motion="on"`). The Meldingen section (`data-sec="onboard"`) hides itself when it is empty.
- Bedrijven defaults to the indeling `combi` (`posState.d`, `POS_GROUPS` in `26-posities.js`); list controls call `refresh('list')`, not `renderList()` directly. The company page builds its sections with `bdSec(title, sub, html)` (desktop) and `block(...)` (phone): add a new detail tile to a section there, in both. The fast mode is the `.fast-tile` itself, shown as `.fast-full` (a fixed dialog) while it runs; `fastDraw` keeps the class in step and stops the fast mode when its page closes.
- Pages are one whole, not a stack of cards: `.tile` has no background or radius, sections and tiles are separated by a thin `border-top: 1px solid var(--rule)`. Do not add card backgrounds, shadows or foldable tiles. On the phone (`mode === 'm'`) `lineChart` drops `markers` (bare line, no pins); the desktop keeps them.
- Two layouts share the data layer: desktop (`#shell`, `page-*`) and phone (`#mshell`, `m-*`). A new tile needs to appear in both.
- Tiles no longer fold (removed in v73): every tile shows its full content. When code measures layout, still keep reads and writes in separate passes and batch them per frame with `rafWork(key, fn)`.
- Expandable overviews are pseudo detail pages (`@account`, `@risk`, `@result`, `@deposits`) registered in `PSEUDO`.
- Keep animations, and honour `prefers-reduced-motion` (`reduceMotion()`). Keep them cheap: animate `transform`/`opacity`, not shadows, sizes or blur. During the zoom into a detail page `#detail` has the class `zooming`, which gives the content a fixed size so only the outer frame moves. The zoom placeholder is `.tile.ghost`; never select plain `.ghost`, that also matches `.btn.ghost` buttons.
- Measurements (`series`) load as a delta (`part=series&since=`) and are kept in IndexedDB (`idbGet`/`idbSet`, with a localStorage fallback). Long line charts are thinned by `thinSets` before drawing.
- When editing files with a script, use Python `str.replace`, not JS `String.replace`: in JS a `$$` in the replacement collapses to `$`, which once broke `$('…')` calls on the live site.
- Site preferences that need no validation (watchlist labels, news filters, limits, FIRE costs, box 3 amounts …) go in `settings.prefs` via `savePrefs(patch)` (the Worker stores it as data, max 40 kB). Per-device layout choices (page customisation, display options, the tour) stay in `localStorage`.
- Explain jargon with `trm(label, key)` and an entry in `GLOSS` (`18-gemak.js`); use `rawKv` instead of `kvList` when a label contains such a term. Heavy calculations go through `runOffThread(fn, input)` (a Web Worker built from a self-contained function).
- Line charts can zoom (pinch, Ctrl + scroll, double click to reset); pass `zoom: false` to `lineChart` to switch it off. New pages register views in `PAGE_VIEWS`; sections wrapped in `.dash-sec[data-sec]` can be reordered and hidden by the user. `.dash-sec` has `content-visibility: auto` (the browser skips sections out of view); it clips what sticks out, so `overflow-clip-margin` leaves room for focus rings and shadows. On the phone, Analyse only fills the open tab (`analyseAll` fills all of them for the pdf report).
- Translations: `EN`, `DE` and `FR` in `13-app.js` map Dutch text to the other language; German and French fall back to English. Add new headings and buttons to `EN` at least.
- `makeDemoData()` powers the keyless demo (`?demo`). **Every new feature needs demo data**, otherwise it is invisible to visitors without a key.
- After changing any file in `docs/`, bump the cache version: every `?v=N` in `index.html`, the precache list and `CACHE = 'tracker-vN'` in `sw.js`, and `VERSION` in `js/01-basis.js`. A new file must also be added to the precache list.

## Checking your work

Before committing:

0. Run `node tools/check-site.mjs` (syntax, duplicate or browser-clashing names, cache version, script list), `node tools/check-toon.mjs` (the news tone lexicon in `docs/js/15-toon.js`), `node tools/check-types.mjs` (TypeScript `checkJs`; fails when a file gets more type findings than `tools/types-baseline.json` allows; after fixing findings run it with `--update`), `node tools/check-vendor.mjs` (the vendored library in `docs/vendor/`: fingerprint against `versions.json` and known advisories; after updating the library run it with `--update`) and `node worker/test/run.mjs` (Worker against mocked APIs and an in-memory SQLite D1). A separate Lighthouse workflow checks the demo against the budget in `lighthouserc.json`; it does not block the deploy. Both run in GitHub Actions; the Pages deploy and the Cloudflare build wait for them. Add a Worker test for every new route, source or fallback.
1. `node --check` every file in `docs/js/` (the module with `--input-type=module` or by importing it) and import `worker/src/index.js` in Node to catch syntax errors. Also check that no top-level name is declared twice across `docs/js/` and none is a property of `window`.
2. Serve `docs/` locally (`python3 -m http.server`) and open `/?demo` at desktop (1360×900) and phone (390×844) size. For changes that may affect speed, run `node tools/meetlat.mjs` (longest task, draw times and elements, phone with a 4× slower CPU) before and after; `--map` measures another checkout. `?perf` shows the same live. Check for console errors and look at screenshots of what you changed, in light and dark.
3. For data handling, also try sparse data: no weeks, one position, no optional sources. Tiles should explain what is missing, never show `NaN`, `undefined` or crash.
4. For Worker changes, exercise the handler against mocked `fetch` and an in-memory D1 stand-in rather than live APIs.

## Commits and deploys

- Commit messages in Dutch, one line describing the user-visible change.
- Pushing to `main` deploys both parts: GitHub Pages serves `docs/`, and Cloudflare builds the Worker from `worker/`. Allow about a minute before verifying live.
- Update the feature table in `README.md` and the endpoint list in `worker/README.md` when you add a feature, source or endpoint.
